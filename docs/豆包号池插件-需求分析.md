## 1. 结论摘要

1. **本项目已有「火山方舟」供应商预设（`db.js:168`），但只能跑文本和图像**。视频走不通——方舟视频是 `/contents/generations/tasks` 异步任务协议，与现有 3 个视频协议（`openai-video` / `agnes-video` / `openai`）**参数结构完全不同**。必须新增协议 `ark-video`。
2. **「号池」当前有一个致命误用点**：现有 429 处理是**死等同一个 Key** 重试（`endpoint.js:456` 的 `sleep([8000,20000,40000])`）。而方舟的 429 有 4 种语义，其中 `QuotaExceeded`（额度耗尽）**等多久都不会恢复**。号池最大的价值不是「额度变多」，而是**让重试变得有意义**。
3. **「号池」必须先定义清楚是哪种**（见 §3）。方舟免费额度是**主账号下共享**的，同主账号开 50 个 Key **不会**增加额度。要真正扩额只能多主账号——这直接影响合规边界与实现方式。
4. 建议形态：**v1 做成内建插件模块**（新建 `server/plugins/doubao/`，通过注册表挂载），而不是先造一套动态插件系统。宿主目前没有插件基建，先落地能力、留好插件契约切面。

## 2. 背景与问题定义

### 2.1 现状：豆包只被"半支持"

| 用途 | 方舟真实接口 | 现有协议能否走通 | 结论 |
| --- | --- | --- | --- |
| 文本 | `POST /api/v3/chat/completions` | ✅ `openai` 协议完全兼容 | 可用 |
| 图像 | `POST /api/v3/images/generations` | ⚠️ `openai` 协议可用，但 `size` 语义不同 | 有坑 |
| 视频 | `POST /api/v3/contents/generations/tasks` → `GET .../tasks/{id}` | ❌ 三个视频协议全不匹配 | **必须新增** |
| 语音合成 | `openspeech.bytedance.com`，非方舟统一 API | ❌ 鉴权维度完全不同 | 独立议题 |

**图像 size 的坑**：`ai.js` 的 `callImage` 默认 `size='1024x1536'`，而 Seedream 用 `"2K"` / `"4K"` / `"1024x1024"` 这类枚举。直填会报 `InvalidParameter`。需要在插件里做尺寸映射表。

### 2.2 痛点：现有重试策略在免费额度场景下是无效功

`endpoint.js` 的 `execute()`：

```js
if (res.status === 429 && retry429 && rateLimitRetries < 3) {
  await sleep([8000, 20000, 40000][rateLimitRetries]);   // ← 68 秒
  rateLimitRetries++;
  continue;                                              // ← 用的还是同一个 apiKey
}
```

对照方舟真实的 429 语义：

| 方舟错误码 | 真实含义 | 换 Key 能否解决 | 等 8/20/40 秒后重试 |
| --- | --- | --- | --- |
| `RateLimitExceeded.EndpointRPMExceeded` | 瞬时请求数超限 | ✅ 能 | 可能有效 |
| `RateLimitExceeded.EndpointTPMExceeded` | token 速率超限 | ✅ 能 | 可能有效 |
| `QuotaExceeded` | **额度耗尽** | ✅ 能（换号即可继续） | ❌ **永远失败，纯浪费 68 秒** |
| `ServerOverloaded` | 服务端过载 | ❌ 不能 | ✅ 应该退避 |

而 `describeHttpError`（`endpoint.js:396`）把 429 一律翻译成"上游限流（免费额度用尽或请求过快）"——**把可换号解决的限流，和等再久也没用的额度耗尽，混成了一句提示**。用户看到的现象就是"卡了 1 分钟然后失败"，且不知道为什么。

**这就是号池要解决的核心问题。**

## 3. 关键澄清：「号池」的两种语义

> ⚠️ 这一节是全文档最重要的部分，选错方向整个设计作废。

方舟官方配额规则：**「免费推理额度，不同模型分别计算，主账号下共享」**；一个主账号最多创建 **50 个 API Key**。

由此推出两种本质不同的号池：

| | **A 类：同主账号 · 多 Key** | **B 类：多主账号** |
| --- | --- | --- |
| 额度总量 | **不增加**（主账号共享） | ×N（每个主账号独立额度） |
| 能解决 | 单 Key 的 RPM / TPM 瞬时限流 | 限流 **＋ 总额度不足** |
| 冲突域 | 同账号并发会互相抢占 | 各账号独立 |
| 合规风险 | 低（官方允许 50 Key） | **中**（多实名账号刷免费额度可能违反活动规则） |
| 获取成本 | 控制台点几下 | 需多个实名手机号 / 主体 |
| 实现差异 | 仅调度层 | 调度层 + 账号生命周期管理 |

**建议**：
- 架构上**统一按 B 类设计**（账号为第一公民，Key 只是账号凭据），A 类退化为 `同一 owner_id 下的多个账号` 的特例。
- 默认**只启用 A 类**（合规安全）；B 类作为可选项，由用户自行导入，插件不提供任何自动注册能力，并在 UI 明示风险。

## 4. 需求目标

| 编号 | 目标 | 衡量方式 |
| --- | --- | --- |
| G1 | 画布与流水线可选用豆包全模态（文本/图像/视频） | 节点下拉可选到"豆包号池"作为来源 |
| G2 | 429 / 401 / 403 触发**自动换号**，而非死等 | 单 Key 额度耗尽后任务仍能继续完成 |
| G3 | 账号状态可见、可控、可恢复 | 面板展示每个号的状态/用量/最近错误，支持手动冷却与恢复 |
| G4 | 额度耗尽不再浪费 68 秒 | `QuotaExceeded` 走快速换号路径，不进入 sleep 重试 |
| G5 | 批量任务（生图/生视频）不因单号限流而整体失败 | 20 镜批量任务在池内完成率 ≥ 95% |

## 5. 非目标（明确不做）

| 不做 | 原因 |
| --- | --- |
| **豆包网页版 / App / 即梦 的 Cookie 池** | 走的是登录态 + 设备指纹风控，属逆向工程。违反服务条款、法律风险高、上游一改动即全线失效，维护成本不可控。**本插件只对接官方 API Key。** |
| 自动注册账号 / 绕过实名 | 违法，不做。 |
| 官方 API Key 的转售 / 对外代理分发 | 违反方舟服务条款。 |
| 修改用户已配置的现有供应商行为 | 号池必须是**新增、可选、可回退**的能力，不影响存量配置。 |
| 并发数突破上游硬限制 | 号池不"破解"限流，只是把请求分配到不同额度域。 |

## 7. 架构设计

### 7.1 三个挂载点（都在现有代码里，不需重构）

| 层 | 文件 | 挂载方式 |
| --- | --- | --- |
| **协议层** | `server/endpoint.js` | `PROTOCOLS` 数组追加 `ark-video`；`builtinSpec()` 加分支；`probeModel()` 加分支 |
| **配置解析层** | `server/ai.js` | `resolveTarget()` 返回前，把 `apiKey` 换成 **池选出的账号凭据**，并附带回 `accountId` |
| **执行层** | `server/endpoint.js` | `execute()` 的 429 分支改为：**分类 → 通知号池 → 换号重试**；接收 `onOutcome` 回调 |

`resolveTarget()` 是整个项目**唯一**的凭据汇聚点——所有文本/图像/视频调用都从这里取 `{baseURL, apiKey, protocol, model}`。号池挂在这里，画布、分镜流水线、Agent 工具链**全部自动获得号池能力**，无需逐处改造。

### 7.2 插件目录与契约

```
server/plugins/
├─ registry.js          # 插件注册表：合并 protocols / providers / 能力声明
└─ doubao/
   ├─ index.js          # 插件入口（manifest）
   ├─ arkVideo.js       # ark-video 协议 spec 生成 + 轮询字段
   ├─ pool.js           # 账号池：选号 / 状态机 / 冷却 / 并发闸
   ├─ models.js         # 模型清单与 id 映射（含 size 枚举映射表）
   └─ health.js         # 探活（复用 probeModel 思路，不消耗生成额度）
```

插件 manifest 声明（**为未来抽成真插件预留的契约**）：

```js
export default {
  key: 'doubao',
  name: '豆包（火山方舟）',
  protocol: 'ark-video',
  baseURLTemplate: 'https://ark.cn-beijing.volces.com/api/v3',
  models: { text: [...], image: [...], video: [...] },
  sizeMap: { '1024x1536': '2K', ... },
  accountPool: { concurrencyDefault: 2, supportsQuotaProbe: true },
}
```

### 7.3 「无限画布」集成方式

不在画布上新增一整套豆包专用节点（会造成节点爆炸），而是**给现有节点加"模型来源"维度**：

| 节点 | 改造 |
| --- | --- |
| `ImageNode` / `VideoNode` / `LlmNode` | 节点内「模型来源」下拉增加 `豆包号池（N 个号可用）` 选项，选中即走池 |
| `DirectorNode` | 新增"豆包导演"预设，默认配 Seedance 2.0 + 9:16（对齐现有短剧生产规格） |
| 顶栏状态区 | 显示 `豆包号池 3/5 可用` 徽标，点击直达号池面板 |
| 节点执行结果 | 卡片上标注**本次实际使用的账号别名**（便于排查"为什么这次慢"） |

## 8. 功能需求

### FR-1 协议层：新增 `ark-video`

| 项 | 要求 |
| --- | --- |
| FR-1.1 | `PROTOCOLS` 追加 `{ key:'ark-video', name:'火山方舟视频', hint:'提交 /contents/generations/tasks，轮询任务状态' }` |
| FR-1.2 | 提交：`POST {base}/contents/generations/tasks`，body 为 `{ model, content:[{type:'text',text},{type:'image_url',image_url:{url}}], resolution, ratio, duration, watermark, generate_audio, seed, camera_fixed }` |
| FR-1.3 | 结果 id 从 `id` 字段取（`cgt-` 前缀）；轮询 `GET {base}/contents/generations/tasks/{{id}}` |
| FR-1.4 | 轮询状态路径 `status`；**完成值必须含 `succeeded`**；失败值含 `failed`；结果路径 `content.video_url` |
| FR-1.5 | 轮询间隔 10s、最大 300 次（对齐现有视频超时预算） |
| FR-1.6 | 首帧/尾帧、参考图按 `image_url` 数组传入（方舟允许多图） |
| FR-1.7 | 产物 URL 会过期 → 必须落盘（现有 `materialize()` 已实现，确认走通） |
| FR-1.8 | `probeModel()` 增加 `ark-video` 分支，用缺参请求判权限 |

### FR-2 账号池核心

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-2.1 | 账号 CRUD：别名、API Key、所属主体(owner)、备注、启用开关 | P0 |
| FR-2.2 | Key 掩码存储与回显（复用现有 `key_hint` 风格），列表不展示明文 | P0 |
| FR-2.3 | 批量导入：一行一个 Key（或 `别名,Key` CSV），支持粘贴整段文本自动清洗 | P0 |
| FR-2.4 | 账号状态机：`active` / `cooling(until)` / `exhausted` / `invalid` / `probation` | P0 |
| FR-2.5 | 自动状态流转：401/403 → `invalid`；`QuotaExceeded` → `exhausted`；限流 → `cooling` | P0 |
| FR-2.6 | 探活恢复：冷却到期后进入 `probation`，连续 3 次成功回 `active` | P1 |
| FR-2.7 | 手动操作：手动冷却 / 立即恢复 / 删除 / 一键全量探活 | P1 |
| FR-2.8 | 用量统计：今日调用数、成功数、429 次数、额度耗尽次数、最近错误 | P1 |
| FR-2.9 | 权重与并发上限：每账号可设 `weight` 与 `max_concurrency` | P2 |
| FR-2.10 | 号池可被多个用途共享，也可按用途隔离（文本/图像/视频各一池） | P1 |

### FR-3 调度策略

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-3.1 | 默认策略 `least-inflight`：当前并发占用最少的可用账号优先 | P0 |
| FR-3.2 | 备选 `round-robin` / `quota-priority`（剩余额度多的优先） | P1 |
| FR-3.3 | **任务亲和锁定**：一次调用从提交到轮询结束**必须锁定同一账号** | **P0** |
| FR-3.4 | 批内亲和（可选）：同一画布/同一剧本的批量任务优先复用同一账号，降低风格漂移 | P2 |
| FR-3.5 | 换号预算：单次调用最多换号 3 次，超限抛「账号池已耗尽」并给出可操作提示 | P0 |

> **FR-3.3 是硬约束**：`execute()` 轮询用的是提交时的同一个 `apiKey`。视频任务提交到 A 号后，若用 B 号轮询会直接 404。号池必须在调用链路上传递 `accountId` 并在整个生命周期内锁定。

### FR-4 执行层改造（核心逻辑）

针对 `execute()` 的重试分支，替换为：

```
收到响应 →
  ├─ 200                     → 成功，通知池：该号记 1 次成功
  ├─ 401 / 403               → 标记 invalid（永久）→ 换号重试（不计入 sleep）
  ├─ 429 + RateLimitExceeded → 该号 cooling(60s)   → 立刻换号重试
  ├─ 429 + QuotaExceeded     → 该号 exhausted      → 立刻换号重试（★ 不 sleep）
  ├─ 429 + ServerOverloaded  → 全局退避 8/20/40s   → 保持原逻辑（换号无意义）
  └─ 其他                    → 按现有 describeHttpError 抛错
```

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-4.1 | `describeHttpError()` 保留可解析的错误码（挂到 `error.code` / `error.upstreamCode`），不再把 4 种 429 揉成一句话 | P0 |
| FR-4.2 | `execute()` 增加 `onOutcome(result)` 回调，供号池记账 | P0 |
| FR-4.3 | 换号后需重新生成 spec（因为 spec 里可能内嵌 api_key 占位符） | P1 |
| FR-4.4 | 全部账号不可用时，错误信息要**说明原因与建议**（例：`账号池 5 个账号均不可用：3 个额度耗尽，2 个鉴权失败`） | P0 |

### FR-5 运维面板（设置 → 第 4 页签「豆包号池」）

| 区域 | 内容 |
| --- | --- |
| 顶部概览 | `可用 3 / 共 5 · 今日调用 128 · 失败 6`，右侧「一键探活」「批量导入」「导出」 |
| 账号表格 | 别名 · Key 掩码 · 状态徽标 · 今日调用 · 成功率 · 最近错误 · 操作（冷却/恢复/删除） |
| 状态徽标配色 | `active`=绿 · `cooling`=黄（显示倒计时） · `exhausted`=橙 · `invalid`=红 · `probation`=蓝 |
| 调度设置 | 策略下拉 · 每号并发上限 · 换号预算 · 冷却时长 |
| 风险提示 | B 类（多主账号）时在面板顶部常驻一行合规提示 |

## 9. 数据模型

新增 2 张表（沿用项目现有 `TEXT` 主键 + `uid()` 风格）：

```sql
-- 账号
CREATE TABLE IF NOT EXISTS pool_account (
  id TEXT PRIMARY KEY,
  pool_id TEXT,                  -- 所属池（按用途隔离时用）
  provider_id TEXT,              -- 绑定到哪个 provider 记录
  alias TEXT,                    -- 别名，如「豆包-01」
  api_key TEXT,                  -- 明文（与项目现有密钥存储方式一致）
  owner_id TEXT,                 -- 主体标识：同 owner 下的号共享额度（A/B 类判定依据）
  status TEXT DEFAULT 'active',  -- active|cooling|exhausted|invalid|probation
  cooldown_until TEXT,
  fail_streak INTEGER DEFAULT 0,
  success_streak INTEGER DEFAULT 0,
  weight INTEGER DEFAULT 1,
  max_concurrency INTEGER DEFAULT 2,
  inflight INTEGER DEFAULT 0,    -- 运行时并发占用
  enabled INTEGER DEFAULT 1,
  last_error TEXT, last_used TEXT,
  create_time TEXT, update_time TEXT
);
CREATE INDEX IF NOT EXISTS idx_pool_account_status ON pool_account(pool_id, status);

-- 用量流水（用于统计与排查，定期清理）
CREATE TABLE IF NOT EXISTS pool_usage (
  id TEXT PRIMARY KEY, account_id TEXT, kind TEXT,
  ok INTEGER, http_status INTEGER, upstream_code TEXT,
  ms INTEGER, create_time TEXT
);
CREATE INDEX IF NOT EXISTS idx_pool_usage_time ON pool_usage(account_id, create_time);
```

`provider` 表补 2 列（沿用 `ensureColumn` 迁移模式，不破坏存量数据）：
- `key_strategy TEXT DEFAULT 'single'` — `single` | `pool`
- `pool_id TEXT`

| GET | `/api/plugins` | 已注册插件与能力声明（为未来插件系统预留） |

## 11. 关键技术风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| **视频任务跨号轮询 404** | 任务永远拿不到结果 | FR-3.3 调用级锁号；轮询复用同一 `apiKey` |
| `QuotaExceeded` 与其他 429 同码 | 误判为限流 → 反复无效重试 | 解析响应体 `error.code` 字符串，按 §FR-4 分类 |
| 图像 `size` 枚举不匹配 | Seedream 报 `InvalidParameter` | 插件内维护 size 映射表 + 兜底透传 |
| 产物 URL 过期 | 素材丢失 | 沿用现有 `materialize()` 落盘；确认视频走通 |
| 并发 2 的队列 × 号池并发上限不匹配 | 号池形同虚设（只有 2 个并发） | 让 `max_concurrency` 与流水线并发联动，或提高批量并发上限 |
| 免费额度用尽无感知 | 批量任务跑到一半全失败 | `QuotaExceeded` 立即标记 + 面板告警 + 任务日志提示剩余可用号数 |
| 数据库并发写 | `node:sqlite` 为同步 API，号池记账需注意 | 记账走内存 + 定期落盘，避免高频写 |

## 12. 合规与风险提示（必须保留在交付物中）

1. **官方 API Key 多账号轮询**：技术上正当，方舟本身允许单主账号 50 个 Key。
2. **多实名主体刷免费额度（B 类）**：可能违反火山引擎活动规则与用户协议，存在**账号封禁、额度清零**风险。插件不提供自动注册，且需在 UI 明示。**建议商业用途使用付费额度。**
3. **绝不实现网页版/App Cookie 池**：见 §5 非目标。
4. **密钥安全**：沿用项目现状（明文存 `weave.db`，仅本机）。号池会放大集中风险——建议导出配置时默认**不含** Key，并在 UI 提示"集中存放 N 个 Key"的风险。
